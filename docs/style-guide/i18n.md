# Internationalization

How an app keeps its user-facing strings out of its code. Today the native app in
`apps/native` is the only workspace with strings to translate; paths below are under
`apps/native/`.

## `src/i18n/index.ts` sets up i18next

`src/i18n/index.ts` imports `intl-pluralrules`, which gives i18next the `Intl.PluralRules` it
needs for plurals, reads the device's language from `expo-localization`, and starts i18next
with English as the fallback for every language. `src/app/_layout.tsx` imports `@/i18n`
first, so every screen can translate.

## One JSON file per domain, no `common.json`

Strings live in `src/i18n/resources/<locale>/`, one file per screen or area, named after it.
English is the only locale today:

```text
src/i18n/
├── index.ts
└── resources/
    └── en/
        ├── home.json         the Home screen
        ├── navigation.json   the tab bar
        └── settings.json     the Settings screen
```

There is no `common.json`. A string two domains share is written in both, so a change to
one screen's copy never changes another's.

## A screen loads its namespace with `useTranslation("<domain>")`

Each file is a namespace. A screen asks for its own, then reads keys inside it:
`src/screens/home/index.tsx` calls `useTranslation("home")` and renders `t("title")` and
`t("api.failed")`; `src/app/(tabs)/_layout.tsx` calls `useTranslation("navigation")` for the
tab titles.

## Tests assert on keys, never on translations

Tests never render a translation. The react-i18next mock in `src/testing/mocks.ts` returns
the key path, `namespace.key`, for every `t` call:

```ts
// in the app
t("title"); // in the "home" namespace → "Home"

// in a test
t("title"); // in the "home" namespace → "home.title"
```

So a test asserts on the key, as `src/app/__tests__/layout.test.tsx` expects the home tab's
title to be `navigation.tabs.home`. A change to the English copy breaks no test, and a test
shows exactly which key a screen uses.
